# Порядок выполнения задач

## Контекст

- Репозиторий: https://github.com/rkhairullin/ilsur_zombie
- Trello: https://trello.com/b/qmahbvMx
- Списки: Roadmap, Backlog, In Progress, Check & Release, Done.
- Приоритет: P0 → P1 → P2, внутри приоритета — порядок карточек с учётом зависимостей.
- Не переносить эти настройки на другие проекты без запроса пользователя.

## Непереходимые границы

1. Не создавать коммиты, не отправлять изменения кода и не создавать PR до явного согласования пользователем конкретного результата и его проверки. «Делай», разрешение начать работу и одобрение идеи не считать одобрением готового результата.
2. Не выполнять merge, squash-merge, rebase-merge, не включать auto-merge и не создавать автоматизацию, которая сливает PR. Мерж выполняет только пользователь, даже если технически у агента есть права.
3. Не делать прямые коммиты в основную ветку и не объединять разные задачи в одну рабочую ветку.
4. Не удалять ветки на основании одного лишь закрытия PR или отсутствия удалённой ветки. Проверять merged=true для конкретного PR и соответствие ветки/коммитов.
5. Не выдавать ограничения среды или непройденные проверки за успех. При невозможности соблюдать порядок остановить зависимые действия, сохранить подготовленный результат и объяснить блокировку. Не обходить ожидание согласования через GitHub API.

## 1. Начать задачу

- Прочитать актуальную карточку, критерии готовности, зависимости и инструкции репозитория. Уточнять только действительно недостающий контекст.
- Проверить текущую ветку, рабочие изменения и доступность основной ветки. Не затирать, не коммитить и не переносить чужие изменения автоматически; использовать отдельный worktree при необходимости и доступности.
- Для новой задачи создать новую локальную ветку от актуальной основной ветки, например `feat/02-aim-and-fire`, `fix/03-hit-detection`, `docs/26-task-workflow`. Если удалённая ветка нужна до согласования, создавать её только на существующем базовом коммите, без отправки изменений.
- Повторную доработку одной задачи вести в её существующей ветке. Новую ветку не создавать на каждую правку.
- До начала реализации перенести карточку в In Progress. Записать имя ветки и краткий объём; не назначать выдуманные сроки.
- По умолчанию вести одну активную задачу; не запускать следующую автоматически без поручения пользователя.

## 2. Реализовать и проверить

- Выполнить только объём задачи; новые идеи записывать отдельно, не расширять задачу молча.
- Проверить diff, сборку и необходимые проверки по существу изменения. Для интерфейса проверять доступными средствами экран, размеры и взаимодействия.
- Для этого проекта использовать `npm run build`, `npm test` и проверки синтаксиса изменённых JS-модулей. Для UI дополнительно проверить переходы, портрет/ландшафт и маленький экран; не считать HTTP-тесты визуальной проверкой.
- Пока пользователь не согласовал результат, оставлять изменения локально без коммита и PR. Не включать секреты, `.env`, зависимости, сборки и результаты тестов в будущий коммит.
- Если пользователь просит доработку, вернуть карточку в In Progress, исправить в той же ветке и повторить затронутые проверки.

## Обязательное покрытие тестами

- Покрывать автоматическими тестами всю реализованную функциональность, включая успешные сценарии, ошибки, граничные значения, переходы состояния и взаимодействие компонентов. Для каждого критерия готовности указывать соответствующий тест; новые функции без тестов не считать завершёнными.
- Для исправления ошибки сначала добавлять регрессионный тест, воспроизводящий её; после исправления он должен проходить. Проверять результат поведения, а не повторять внутреннюю реализацию.
- Для игровой логики писать модульные тесты: урон, попадания, боеприпасы, перезарядка, таймеры, комбо, выпадение предметов, волны, боссы и рост сложности по мере реализации. Управлять временем и случайностью детерминированно.
- Для API и хранения данных добавлять интеграционные тесты: доступ, валидация, ошибки сети, сохранение, повторная отправка и защита от двойного начисления по мере реализации этих функций.
- Для интерфейса добавлять исполняемые браузерные E2E-тесты: меню, арена, пауза, возврат, касания и их отмена, одновременные касания, смена ориентации, сворачивание, полноэкранный режим и его отказ по мере реализации. Проверять Chromium и WebKit, маленький горизонтальный экран и портретную подсказку.
- Для визуальных изменений добавлять проверки раскладки и визуальные регрессионные снимки; не обновлять эталоны вслепую. Ручная проверка на телефоне дополняет автоматическую, но не заменяет её.
- Настроить измерение покрытия всего исполняемого кода приложения, сервера и служебных скриптов, включая файлы, которые тесты не импортировали. Цель и порог — 100% строк, функций и ветвей. Не снижать порог, не исключать код и не добавлять фиктивные проверки ради зелёного отчёта. Сгенерированные файлы и сторонние зависимости не считать собственным кодом; обоснованные технические исключения отдельно согласовывать с пользователем.
- Не считать 100% покрытия доказательством отсутствия ошибок: дополнительно проверять требования и реальные сценарии. Для Markdown, конфигурации и стилей без исполняемой логики использовать соответствующие проверки структуры, ссылок, сборки, раскладки и визуального поведения вместо искусственных unit-тестов.
- Сделать тесты воспроизводимыми: явно объявлять зависимости и команды, сохранять lock-файл при наличии зависимостей. Все обязательные наборы, включая браузерные, должны запускаться документированной командой и в CI для каждого PR; падение тестов или порога покрытия должно завершать проверку с ошибкой.
- Перед передачей результата запускать все затронутые наборы, сборку и отчёт покрытия. В карточке и PR записывать команды, итог, измеренные проценты по категориям, соответствие критериям и оставшиеся пробелы. Без отчёта писать «покрытие не измерено», а не «всё покрыто».
- Если среда не позволяет запустить тесты, использовать доступный CI; если и он недоступен, явно отметить блокировку. Допускается передать результат в Check & Release для разблокировки, но не объявлять задачу готовой к выпуску и не переносить в Done до успешных обязательных проверок. Создать коммит/PR с этой блокировкой только по явному разрешению пользователя; это не отменяет требования тестирования до завершения.
- При обнаружении старых пробелов перечислять их отдельно и учитывать как незавершённую проверку соответствующей функции. Изменение этого документа само по себе не создаёт тесты и не закрывает прежние пробелы.

## 3. Передать на тестирование

- После завершения реализации и доступных проверок перенести карточку в Check & Release.
- Обновить описание карточки, сохранив требования и полезный контекст: что изменено, ветка, выполненные проверки, ограничения, что осталось проверить. PR пока отсутствует — так и указать.
- Сообщить пользователю:
  1. Что изменилось.
  2. Как запустить и открыть результат: точные команды, адрес, нужные условия сети/устройства.
  3. Нумерованные действия тестирования и ожидаемый результат каждого.
  4. Что уже проверено, что не проверено и почему.
  5. Что коммит и PR будут созданы только после согласования.
- Дождаться явного подтверждения применительно к этому результату: например, «Проверил, всё хорошо, создавай PR». Не считать молчание согласием.

## 4. После согласования

- Перед коммитом проверить, что diff соответствует согласованному результату. Если поведение существенно изменилось после проверки, снова передать на тестирование.
- Создать осмысленный коммит только с файлами задачи, отправить рабочую ветку и открыть один PR в основную ветку. При существующем PR обновлять его после согласования очередных правок, а не создавать дубликат.
- В PR указать проблему, итоговое поведение, ссылку на Trello, выполненные проверки и ограничения. Для UI приложить скриншот, если он действительно получен.
- Записать ссылку на PR в карточку. Оставить статус Check & Release до мержа и проверки выпуска, если выпуск входит в задачу.
- Сообщить пользователю ссылку на PR. Не выполнять мерж и не обещать автоматическое наблюдение за ним.

## 5. После мержа пользователем

- По сообщению пользователя или при следующем продолжении работы проверить состояние PR через GitHub. Без расписания не обещать фоновую проверку или мгновенную очистку.
- Подтвердить `merged=true`, нужные репозиторий, head-ветку и коммит. При наличии новых несогласованных коммитов или изменений остановить удаление.
- Выполнить fetch с prune. В чистом рабочем дереве переключиться на основную ветку и обновить её только fast-forward; при расхождении не делать reset.
- Убедиться, что ветка не используется другим worktree и не содержит несохранённой работы. Удалить только локальную ветку завершённой задачи обычным `git branch -d`.
- При squash/rebase обычное удаление может отказать. Не применять `-D` автоматически: сначала подтвердить по GitHub, что именно сохранённый head был слит, и проверить отсутствие дополнительных изменений. Если безопасное удаление не доказано, сохранить ветку и объяснить причину.
- Удалённую ветку должна удалять настройка GitHub Automatically delete head branches. Если она осталась, проверить ограничения, сообщить пользователю; не удалять другие ветки.
- Перенести карточку в Done после подтверждённого мержа и выполнения требований выпуска. Если осталась проверка размещения, оставить Check & Release и указать её явно.

## Настройка GitHub

Попросить пользователя один раз открыть Settings → General → Pull Requests → Automatically delete head branches в репозитории и включить флажок. Настройка относится к удалённым веткам после мержа, не к локальным. Защита веток и rulesets могут препятствовать удалению. Не менять настройки по собственной инициативе, если пользователь запросил только инструкцию.

## Исключение для существующего результата

PR №1 был создан до введения этого порядка. Не закрывать и не переписывать его историю автоматически. Следующие изменения в нём публиковать только после нового согласования. Для новых задач применять весь порядок с начала.
